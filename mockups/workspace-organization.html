Five ways to lay out a project on disk and show it in the UI. The thread list and chat stay the same; the Files panel (right) and the on-disk tree (middle) change. Switch with the floating pill or keys 1–5.

1

Plain folders

the project folder is just a folder; the app adds a hidden .aithing/ for history
On disk
brand-refresh-q4/
├── AGENT.md                 # brief + rules, read by every agent
├── style.md
├── inputs/                  # whatever the user drops in
│   ├── ref-01.jpg
│   ├── ref-02.jpg
│   └── ref-03.jpg
├── hero/                    # agent-chosen structure
│   ├── a-01.png … a-04.png
│   ├── b-01.png … b-04.png
│   └── picks/
│       └── b-03.png
├── generated/               # default when the agent gives no path
└── .aithing/                # hidden: versions/, thread logs
    └── versions/hero/b-03.png/ v1.png v2.png manifest.json
Good
  • Zero learning curve; Finder/Explorer, Dropbox, git all work as-is.
  • Agents name and organise files the way the user asks in plain language.
  • Instructions are just markdown in the root, which is what coding agents already expect.
Weak
  • Nothing tells the UI which images are references and which are outputs, so "attach a reference" is a guess.
  • Different threads invent different layouts; the folder drifts.
  • Picks, trash and notes need conventions the agent has to be told about each time.

This is what the harness does today. Every other option is a layer of convention or metadata on top of it.

Typed folders

four fixed top-level folders by role; anything else is free-form
On disk
brand-refresh-q4/
├── brief/                   # instructions: everything here is loaded into the agent's context
│   ├── AGENT.md
│   ├── style.md
│   └── audience.md
├── refs/                    # reference images; never written by agents
│   ├── ref-01.jpg
│   ├── logo/ logo.svg  logo-dark.png
│   └── moodboard/ 14 files
├── out/                     # everything agents generate, grouped as they like
│   ├── hero/ a-01.png … b-04.png
│   └── social/
├── picks/                   # curated: copies or links of the keepers
│   └── hero-b-03.png → out/hero/b-03.png@2
└── .aithing/  versions/  trash/
Good
  • The UI knows what a file is by where it lives: refs get an "attach" affordance, outputs get "iterate", brief gets an editor.
  • Simple safety rule: agents can read refs/ and brief/ but only write under out/.
  • Still plain folders; nothing breaks outside the app.
Weak
  • An output that becomes a reference has to be copied or linked into refs/; two places for one image.
  • Four buckets is still a taxonomy the user must accept.
  • out/ grows without structure unless threads are told where to write.

3

Thread-scoped outputs

each thread owns a folder; the project has a shared library
On disk
brand-refresh-q4/
├── AGENT.md
├── library/                 # shared across threads: refs, logos, past picks
│   ├── ref-01.jpg  ref-02.jpg
│   └── hero-b-03.png           # promoted from a thread
└── threads/
    ├── 2026-09-27-hero-warm/  # = "Hero exploration — warm palette"
    │   ├── brief.md            # the first message, editable
    │   ├── refs/ ref-02.jpg → ../../library/ref-02.jpg
    │   ├── a-01.png … b-04.png
    │   ├── notes.md            # the agent's running notes
    │   └── .thread/ log.jsonl versions/
    ├── 2026-09-28-logo-bleed/
    └── 2026-09-29-social-crops/
Good
  • Deleting a thread deletes its mess. Opening a thread shows exactly what it made.
  • The folder is the thread: sharing it (zip, Dropbox link) shares the whole story including notes.
  • Threads cannot trample each other's files, so parallel agents are safe by construction.
Weak
  • Cross-thread work ("fix the logo on yesterday's hero") means promoting files to the library first.
  • Dated folder names get long and the project view is a list of threads rather than of work.
  • Iterating across threads breaks the version chain unless promotion keeps history.

4

Flat library with metadata

no folders; every file has an id and tags, the UI is a filtered gallery
On disk
brand-refresh-q4/
├── AGENT.md
├── library.json             # the index: one record per asset
│   { "id":"k7f2", "file":"k7f2-hero-b-03.png", "kind":"output",
│     "tags":["hero","direction-b","pick"], "thread":"hero-warm",
│     "refs":["a1c9@1"], "prompt":"Flat editorial hero…", "model":"gpt-image-2" }
├── assets/                  # everything, flat, id-prefixed so names never collide
│   ├── a1c9-ref-01.jpg
│   ├── a1c9-ref-01.v1.jpg      # versions sit next to the file
│   ├── b77e-style-guide.md
│   ├── k7f2-hero-b-03.png
│   ├── k7f2-hero-b-03.v1.png
│   └── … 240 files
└── .aithing/ cache/ thumbs/
Good
  • One image can be a reference, an output and a pick at once; no copies.
  • Search and filters (by thread, model, tag, "used as ref") are cheap; lineage is explicit in the index.
  • Agents address assets by short id, which is robust to renames.
Weak
  • The folder is unreadable without the app: 240 id-prefixed files in one directory.
  • The index is a second source of truth that can drift from disk (external edits, deletions).
  • Agents lose the "just write a file" simplicity; every write must go through a tool that updates the index.

5

Assets as versioned objects

an image is a folder: its versions, branches and notes live inside it
On disk
brand-refresh-q4/
├── BRIEF.md
├── refs/ ref-01.jpg  ref-02.jpg  ref-03.jpg     # plain files: refs do not iterate
└── assets/
    ├── hero-b.image/          # one asset = one folder with a suffix the app recognises
    │   ├── current.png          # always the latest chosen version (hard link)
    │   ├── v1.png  v2.png  v3.png
    │   ├── alt-cooler/ v1.png v2.png   # a branch: "try it cooler" without losing the main line
    │   ├── notes.md             # prompt per version, agent comments, your comments
    │   └── asset.json           # lineage, refs, model, thread per version
    ├── hero-a.image/
    └── tavern-interior.image/
Good
  • Iteration is the primary object: "make it warmer" is v4 of hero-b, not a new file to name.
  • Branches let you explore without fear; compare any two versions side by side.
  • current.png keeps it usable by anything that just wants an image.
Weak
  • Folders-as-files confuse other tools: a drag-and-drop gives you a directory.
  • Batch exploration (12 variants at once) does not fit a single linear asset; siblings need a rule.
  • Heavier on disk and on the mental model when most images never get iterated.

Today's harness sits between 1 and 5: plain files on disk, with a hidden per-file history. This option makes that history visible in the folder itself.
